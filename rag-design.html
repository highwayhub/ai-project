RAG 方案设计

以 KnowEngine 为基础，把文档、业务表和关系图谱接到同一问答入口。入库时按资料和用途选择处理方式，提问时按问题选择数据源，再把证据交给模型生成回答。

一、文档前置处理阶段

把文件整理成可检索、可维护的知识，并在入库时保留不同资料的结构。

MinerU 把复杂版面转为可切分的 Markdown

PDF 和 Word 走 MinerU。服务从解析包提取 Markdown 和配图，上传到 MinIO，并在 Markdown 中回填图片地址和可检索的图片描述。已有 Markdown 走直接处理路径。

MinerU 4.x 开源版可解析的格式

  • PDF（含扫描件）与图片：.pdf、.png、.jpg、.jpeg、.webp、.gif、.bmp、.tiff、.jp2。
  • Office 与富文本：.doc、.docx、.ppt、.pptx、.xls、.xlsx、.rtf。
  • OpenDocument 与版式文档：.odt、.ods、.odp、.epub、.ofd。
  • 网页、网页归档与表格文本：.html、.htm、.shtml、.mhtml、.mht、.csv、.tsv。

纯文本 .txt、.md、.markdown、.rst、.tex 可直接读取。项目接入更多格式时，需要按部署版本扩展入库路由并适配解析结果。

本地部署与禅道接入方案 在公司内网运行 MinerU，由同步服务按禅道版本提供的接口或导出方式读取授权范围内的正文与附件。Markdown 正文直接进入切分，富文本正文可导出为 HTML，支持的附件交给内网 MinerU 解析，再切分入库。保留禅道文档 ID、版本、原文链接与可见范围，用于增量更新、引用跳转和检索前的权限过滤。

适合 扫描件和图文手册。用 #、##、### 表达章、节、小节，标题切分才能沿着章节走。原件层级模糊时，可在入库前整理标题，或选择适合该文档的其他切法。

让上传者选择用途和切分方式

文档检索型 转换完成后由用户发起切分。技术规范适合按标题，纯文本可按长度，有明确边界的记录可用分隔符或正则，也可选智能切分。Excel / CSV 用表格切分器，例如把一行写成「团队：支付；级别：P1」，再作为文本 Chunk 供检索。

数据查询型 Excel 首次按表头建表，列默认用 VARCHAR。后续上传校验表结构，匹配后替换旧行。表结构在 table_meta 登记，由 NL2SQL 在检索阶段读取。服务依赖、负责人等关系数据由独立流程维护到 Neo4j。

Chunk 双写支撑热点更新和版本迭代

切分后先把正文、chunkId、父子关系和版本落到 MySQL。事务提交后异步把可检索分段的正文和向量写入 ES，并回写索引 ID 与状态。ES 承担召回，MySQL 承担编辑、追溯和重建。

热点修订 可独立修改子分段，对已索引子段重建向量，并同步父段、清理父段的 Redis 缓存。整版迭代 保留各版分段，新版索引就绪后清理旧索引。文本历史版本重新启用时，可用保留的分段重建索引。

分段与版本切换分段热更新

父子分段兼顾命中精度和上下文

标题切分遇到过长章节时，保存完整章节为父段，并将小段向量化。命中子段后按 parentChunkId 回溯父段，优先读 Redis，缺失时查 MySQL。短章节可直接索引。

例如 搜索「Go 服务回滚命令」能命中小段，回溯整节后还能看到执行前置条件和回滚后的验证步骤。小段负责定位，父段把同一章节的证据补完整。

二、文档检索召回阶段

识别业务领域，选择能回答该问题的数据源，最后把证据和回答规则交给模型。

意图识别、检索提示词和回答提示词各有职责

源码提供结构化意图和按意图加载提示词的机制。以下用公司知识库说明如何适配。

检索前 识别前端、后端（Java / Go）、业务安全、业务运维、风控安全等领域，并提取服务、版本、环境等条件。「订单服务回滚」可识别为业务运维，再结合会话补全服务名和环境。

检索时 领域可用于限定文档候选范围，改写后的问题用于选数据源。走 SQL 或 Cypher 时，使用该路专用提示词和表或图结构生成查询。

生成时 按意图选系统提示词，再注入检索后的证据。例如让运维回答按「前置条件、操作步骤、验证」组织，Java 回答注明框架及版本，风控安全回答区分策略口径与例外。

选择适用场景

三源路由实现

BGE-Rerank 把真正能回答问题的证据排到前面

文档路由使用 Elasticsearch 的向量近邻（HNSW）和全文匹配（默认 BM25）分别召回。两路各自回溯父段后，RRF 按名次合并候选。BGE 再逐对评估「问题与片段」，筛掉弱相关内容。项目用本地 ONNX 做精排，SQL / Cypher 的结构化结果直接进入聚合。

公司 CI/CD 案例「我们用 GitLab 管代码，怎么让合并到 main 后，Jenkins 自动构建镜像并部署到测试环境？」

  • 《GitLab CI/CD 快速入门》命中 GitLab、构建和部署等关键词，讲的是 GitLab Runner 的流水线。
  • 《Jenkins 生产发布手册》也讲 Jenkins 部署，采用人工审批，目标是生产环境。
  • 《研发平台接入指南》解释如何配置 GitLab Webhook，让 main 的 push 事件触发 Jenkins。
  • 《测试环境发布规范》解释如何在 Jenkinsfile 中调用公司共享库，构建并推送镜像，再部署到测试环境。

BGE 把完整问题和每段候选原文一起打分，更有机会把说明「GitLab 怎么触发 Jenkins」和「Jenkins 怎么发布到测试环境」的两段证据提到前面。项目精排后最多保留 5 段，排位会影响大模型看到哪些资料。两段证据都需要先被召回。

高频文档问答以人工审核后的答案复用

定期按语义整理近七天的高频首问，员工审核后才可发布。ES 匹配相似问法，MySQL 校验发布状态、有效期和来源版本。命中可直接返回审核答案，未命中继续正常召回。

适合 允许公开复用、答案稳定的 FAQ，例如公开的开发者接入入口。引用版本变化、撤销公开权限或答案过期后，缓存停止复用。项目默认关闭此功能。

三、RAG 权限体系设计

现有代码按访客、车主、客服三档过滤。以下是面向企业知识库的两种扩展方案，均为待实现设计。

现有角色规则

方案一 · 复用外部权限体系

以禅道为例，RAG 负责切分、向量化和召回。一份知识文档对应一个外部文档 ID，同一文档的所有 Chunk 共用这个 ID。ES 保存正文、向量及过滤所需的 user_id、dept_id、job_level 等元数据。

提问时由服务端获取外部授权的知识库、项目或文档范围，再叠加部门和职级条件。部门与职级可由对接的组织目录补齐，授权范围以外部系统为准。

优点 复用已有账号和授权规则，权限管理与 RAG 解耦。代价 依赖外部认证与授权服务的可用性。

方案二 · RAG 自建数据库 RBAC

MySQL 关联 user、role、dept、document，用用户角色和角色授权关系确定可访问的知识库或文档，再按部门、职级细化范围。

沿用 MySQL 与 ES 双维护。MySQL 保存授权规则和文档可见范围，ES 保存用于召回的 Chunk 和权限元数据。每次召回前先查资源权限，无权则直接返回。

优点 认证、授权和检索均可独立运行。代价 需要维护组织关系、职级和角色授权，并及时同步调岗、离职等变化。

两种方案共用的文档可见规则

可见性 visibility在已授权的知识库及资源范围内，谁能看
公开 PUBLIC有该知识库访问权限的用户，可以跨部门阅读。
部门内 DEPTdept_id 在用户授权的部门范围内，且用户职级 ≥ 文档的最低可见职级。
私密 PRIVATE仅文档所有者可见，以 user_id 匹配登录身份。上级同样按所有者规则校验。

职级约定 job_level 使用整数，数值越大职级越高。文档门槛可默认取发布者职级。比如运维职级 5 能看本部门门槛为 3 或 5 的资料，访问其他部门仍需单独授权。

撤权处理 授权不可用时拒绝受限检索。权限收紧后，在片段交给模型前按最新授权复核，并同步更新 ES 元数据、失效关联问答缓存。

四、RAG 的评测方案

用同一批业务问题对比每次改动，分别判断证据有没有找对、答案有没有用对。

现有评测入口 KnowEngine 的 GET /dataset/generate 复用 RAG 对话流程，输出 question、answer 和引用文本 references。仓库提供样本生成能力，RAGAS 批量评分属于以下接入设计。

样本生成接口

改造为可回归的 RAGAS 评测

  1. 固定题集。 覆盖文档问答、精确取数、多跳关系，以及无答案和容易混淆的问法。由业务同事标注参考答案、证据和预期数据源。
  2. 导出实际证据。 将原问题、模型回答和最终注入的上下文映射到 user_input、response、retrieved_contexts，将人工答案写入 reference。在注入前采集有序上下文，保留 SQL / Cypher 返回的证据，并记录路由和文档版本。
  3. 离线跑分并回归。 Python 批量调用评测入口，交由 RAGAS 评分。固定题集、知识版本和评委模型，关闭问答缓存对比基础链路。用相同候选对比 BGE 精排开关，并记录端到端 P95 延迟。
